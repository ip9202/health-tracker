# SPEC-AI-001: 인수 기준 (Acceptance Criteria)

---

## 1. 개요 (Overview)

본 문서는 AI 기반 건강 분석 및 추천 시스템의 인수 기준을 정의합니다. 모든 시나리오는 Given-When-Then (Gherkin) 형식으로 작성되었습니다.

---

## 2. 기능적 인수 기준 (Functional Acceptance Criteria)

### Scenario 1: InBody 기록 저장 후 AI 분석 자동 트리거

**Given** 사용자가 로그인 상태이고
**And** OCR로 추출된 InBody 데이터가 있으며
**And** AI 분석이 이전에 수행되지 않았을 때

**When** 사용자가 "저장(Confirm)" 버튼을 클릭하면

**Then** 시스템은 InBody 데이터를 데이터베이스에 저장해야 하고
**And** 백그라운드에서 AI 분석을 자동으로 시작해야 하며
**And** 사용자에게 "AI 분석 진행 중" 상태를 표시해야 한다

---

### Scenario 2: AI 분석 완료 후 결과 표시

**Given** 사용자가 로그인 상태이고
**And** InBody 기록이 데이터베이스에 저장되어 있으며
**And** AI 분석이 성공적으로 완료되었을 때

**When** 사용자가 InBody 상세 페이지를 새로고침하거나 접근하면

**Then** 시스템은 AI 분석 결과를 표시해야 하고
**And** 건강 상태(healthStatus), 건강 점수(healthScore)를 표시해야 하며
**And** 위험 요소(riskFactors) 목록을 표시해야 하고
**And** 운동 추천(recommendations) 목록을 표시해야 하며
**And** 주의 사항(warnings)을 표시해야 한다

---

### Scenario 3: AI 분석 결과 캐싱

**Given** 사용자가 로그인 상태이고
**And** InBody 기록에 대한 AI 분석이 이미 존재할 때

**When** 사용자가 AI 분석을 다시 요청하면

**Then** 시스템은 저장된 분석 결과를 즉시 반환해야 하고
**And** 새로운 AI API 호출을 수행하지 않아야 하며
**And** "캐시된 결과"임을 표시해야 한다

---

### Scenario 4: AI API 호출 실패 시 재시도

**Given** 사용자가 로그인 상태이고
**And** InBody 기록이 데이터베이스에 저장되어 있으며
**And** AI API가 첫 번째 호출에 실패했을 때

**When** 시스템이 AI 분석을 시도하면

**Then** 시스템은 1초 후 재시도를 수행해야 하고
**And** 최대 3회까지 재시도해야 하며
**And** 모든 재시도가 실패하면 사용자에게 "분석 실패" 메시지를 표시해야 한다

---

### Scenario 5: 데이터 부족으로 인한 제한된 분석

**Given** 사용자가 로그인 상태이고
**And** 사용자의 InBody 기록이 3개월 미만일 때

**When** AI 분석이 수행되면

**Then** 시스템은 "데이터 부족으로 인한 제한된 분석" 메시지를 포함해야 하고
**And** 현재 데이터 기반의 기본 분석은 제공해야 하며
**And** 추이 분석은 "데이터 부족"으로 표시해야 한다

---

### Scenario 6: BMI 25 이상 사용자에 대한 체중 감량 추천

**Given** 사용자가 로그인 상태이고
**And** 사용자의 BMI가 25 이상일 때

**When** AI 분석이 수행되면

**Then** 시스템은 체중 감량 추천을 우선순위 높게 표시해야 하고
**And** 유산소 운동 추천을 포함해야 하며
**And** 칼로리 소모 관련 팁을 제공해야 한다

---

### Scenario 7: 체지방율 비정상 시 유산소 운동 추천

**Given** 사용자가 로그인 상태이고
**And** 사용자의 체지방율이 정상 범위를 벗어났을 때

**When** AI 분석이 수행되면

**Then** 시스템은 체지방 감소를 위한 유산소 운동 추천을 포함해야 하고
**And** 위험 요소에 "체지방 과다"를 표시해야 하며
**And** 주의 사항에 건강 위험을 알려야 한다

---

### Scenario 8: 골격근량 평균 이하 시 근력 강화 추천

**Given** 사용자가 로그인 상태이고
**And** 사용자의 골격근량이 평균 이하일 때

**When** AI 분석이 수행되면

**Then** 시스템은 근력 강화 운동 추천을 포함해야 하고
**And** 위험 요소에 "근육량 부족"을 표시해야 하며
**And** 추천에 저항 운동 루틴을 제공해야 한다

---

## 3. 보안 인수 기준 (Security Acceptance Criteria)

### Scenario 9: 미인증 사용자의 AI 분석 요청 거부

**Given** 사용자가 로그아웃 상태일 때

**When** 사용자가 AI 분석 API를 호출하면

**Then** 시스템은 401 Unauthorized 응답을 반환해야 하고
**And** "로그인이 필요합니다" 메시지를 표시해야 하며
**And** AI API는 호출되지 않아야 한다

---

### Scenario 10: 다른 사용자의 분석 결과 접근 차단

**Given** 사용자 A가 로그인 상태이고
**And** 사용자 B의 InBody 기록 ID를 알고 있을 때

**When** 사용자 A가 사용자 B의 분석 결과를 요청하면

**Then** 시스템은 403 Forbidden 응답을 반환해야 하고
**And** "접근 권한이 없습니다" 메시지를 표시해야 한다

---

### Scenario 11: 개인정보 포함 방지

**Given** 사용자가 로그인 상태이고
**And** InBody 데이터에 이름(name) 필드가 포함되어 있을 때

**When** AI 분석을 요청하면

**Then** 시스템은 이름을 AI API 요청에서 제외해야 하고
**And** 건강 데이터만 포함해야 한다

---

## 4. 데이터 검증 인수 기준 (Data Validation Acceptance Criteria)

### Scenario 12: AI 응답 스키마 검증

**Given** 사용자가 로그인 상태이고
**And** AI가 분석 결과를 반환했을 때

**When** 시스템이 AI 응답을 받으면

**Then** Zod 스키마 검증을 수행해야 하고
**And** healthStatus가 문자열인지 확인해야 하며
**And** healthScore가 0-100 범위인지 확인해야 하고
**And** riskFactors, recommendations, warnings가 배열인지 확인해야 하며
**And** 검증 실패 시 "분석 결과 형식 오류"를 반환해야 한다

---

### Scenario 13: AI 응답 누락 필드 처리

**Given** 사용자가 로그인 상태이고
**And** AI 응답에 healthScore 필드가 누락되었을 때

**When** 시스템이 AI 응답을 받으면

**Then** Zod 검증이 실패해야 하고
**And** "필수 필드 누락" 오류를 반환해야 하며
**And** 불완전한 데이터를 저장하지 않아야 한다

---

## 5. UI/UX 인수 기준 (UI/UX Acceptance Criteria)

### Scenario 14: AI 분석 진행 상태 표시

**Given** 사용자가 로그인 상태이고
**And** AI 분석이 진행 중일 때

**When** 사용자가 InBody 상세 페이지를 조회하면

**Then** 시스템은 로딩 인디케이터를 표시해야 하고
**And** "AI 분석 진행 중..." 메시지를 표시해야 하며
**And** 진행 상태를 실시간으로 업데이트해야 한다

---

### Scenario 15: AI 분석 실패 시 사용자 친화적 메시지

**Given** 사용자가 로그인 상태이고
**And** AI 분석이 실패했을 때

**When** 시스템이 실패를 감지하면

**Then** 사용자에게 "분석에 실패했습니다" 메시지를 표시해야 하고
**And** "다시 시도" 버튼을 제공해야 하며
**And** 기술적 오류 메시지는 숨겨야 한다

---

### Scenario 16: 재분석 요청 기능

**Given** 사용자가 로그인 상태이고
**And** InBody 기록에 대한 AI 분석이 이미 존재할 때

**When** 사용자가 "재분석" 버튼을 클릭하면

**Then** 시스템은 새로운 AI 분석을 시작해야 하고
**And** 이전 분석 결과를 덮어써야 하며
**And** 진행 상태를 표시해야 한다

---

## 6. 엣지 케이스 (Edge Cases)

### Scenario 17: 타임아웃 발생

**Given** 사용자가 로그인 상태이고
**And** AI API가 30초 이내에 응답하지 않을 때

**When** 타임아웃이 발생하면

**Then** 시스템은 "요청 시간 초과" 메시지를 표시해야 하고
**And** 백그라운드에서 재시도를 계속해야 하며
**And** 완료 시 알림을 제공해야 한다

---

### Scenario 18: 빈 InBody 데이터

**Given** 사용자가 로그인 상태이고
**And** InBody 데이터가 누락되거나 비어있을 때

**When** AI 분석을 요청하면

**Then** 시스템은 "분석 가능한 데이터가 없습니다" 메시지를 표시해야 하고
**And** AI API를 호출하지 않아야 한다

---

### Scenario 19: 동시 다중 분석 요청

**Given** 사용자가 로그인 상태이고
**And** 사용자가 여러 InBody 기록에 대해 동시에 분석을 요청할 때

**When** 시스템이 요청을 받으면

**Then** 각 요청을 독립적으로 처리해야 하고
**And** 순서대로 완료되지 않아도 되며
**And** 각 결과를 올바른 기록에 연결해야 한다

## 8. Definition of Done

기능이 완료로 간주되기 위해서는 다음 모든 조건을 충족해야 합니다:

1. **구현 완료**
   - [ ] 모든 필수 기능이 구현됨
   - [ ] 코드 리뷰 통과
   - [ ] 단위 테스트 통과

2. **품질 보증**
   - [ ] 통합 테스트 통과
   - [ ] E2E 테스트 통과
   - [ ] 테스트 커버리지 85% 이상

3. **문서화**
   - [ ] API 문서 작성 완료
   - [ ] 사용자 가이드 작성 완료
   - [ ] 코드 주석 충분

4. **배포 준비**
   - [ ] 환경 변수 설정 완료
   - [ ] 데이터베이스 마이그레이션 완료
   - [ ] 프로덕션 배포 테스트 통과

## 9. 테스트 도구 및 방법 (Testing Tools & Methods)

### 9.1 단위 테스트

- **도구:** Vitest
- **대상:** AI 서비스, Zod 스키마, API 라우트
- **커버리지 목표:** 85% 이상

- **도구:** Vitest + Supertest
- **대상:** end-to-end AI 분석 흐름
- **시나리오:** 위 19개 시나리오

### 9.3 E2E 테스트

- **도구:** Playwright
- **대상:** 사용자 인터랙션 흐름
- **시나리오:** 핵심 경로 5개

### 9.4 성능 테스트

- **도구:** Vitest Benchmark
- **대상:** API 응답 시간, 캐시 적중률
- **목표:** 평균 3초 이내
